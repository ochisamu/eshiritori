Codexへの実装開始プロンプト

同梱の requirements.txt を最初に最後まで読み、その内容を受入契約として、独自の連戦型イラストしりとりゲームを実装してください。いま依頼しているのは計画の説明だけでなく、ゲーム本体・本番画像・読み辞書・テスト・起動可能な配布物までの制作です。過去の別プロジェクトや原稿作成とは無関係です。

目標
・標準操作は画像をタップして回答。毎回かな入力を強制しない。
・画像に対応する承認済み読みから、現在の開始音に合う非終端語を固定優先順で選び、正解後に読みと理由を見せる。全裏読みを先に見せない。
・発見済み読みの明示選択と任意のかな入力で戦略を深める。
・CPUと交互に遊び、勝敗後は1操作で次戦へ。連戦の回数上限なし。
・最終的に意味の異なる本番品質の画像生成アセット1000種類以上。読みは目標5000、必須3000以上と、本文の分布・品質条件を満たす。
・ブラウザ向けのローカル静的ゲーム。実行時の外部API、課金、ログイン、画像CDNは不要。

まず行うこと
1. 現在の作業先、既存プロジェクトと指示、ランタイム、lockfile、テスト環境を確認し、既存の無関係な作業を壊さない。新規ならTypeScript strict + React + Viteを使う。
2. 画像生成ツールの実在と能力、保存方法、利用枠・費用・権限を調べる。使えないAPIを仮定しない。未知の支払い、予算増額、秘密鍵の保存、権限拡大、外部公開は無断で実行しない。
3. requirements.txtの版とhashを記録し、作業キュー、WORK_LOG.txt、BLOCKERS.json、NEXT_ACTIONS.json、acceptance-report.jsonの初期形を作る。
4. 純粋な判定器、タップ候補解決器、seed付き盤面生成器、CPU、保存を先に分離する。かな正規化の固定例を最初のテストにする。盤面検証は実CPUと実UIで選べる手を使う。
5. 生成済み・審査済み64種類の本番品質スライスで、タイトル→回答→勝敗→次戦→保存復帰を実際に遊べる状態へ進める。その後256、1000へ拡張する。

進め方
コードとアートのキューを分け、画像待ちでも独立した実装・テストを続ける。生成前に裏読みの視覚的根拠を設計し、生成後の絵で本当に成立するか再確認する。生成回数と再試行には本文の上限を適用し、予算・利用枠は承認済み範囲だけ使う。
同じ絵の色違い、左右反転、別サイズ、再切り抜きで1000種類を水増ししない。別々に計画した概念を1枚の生成シートにまとめ、個別に切り出してQAする方式は可。仮画像・絵文字・SVGだけで本番完成にしない。
安全で可逆的な未指定事項は本文の既定値で進め、不要な質問で止めない。不具合は再現→修正→回帰テストを繰り返す。要件の削除や閾値の引下げで成功にしない。
Vitest/Playwright等は実際の利用可能性を確認して使う。コマンドやブラウザを導入しただけで実行済みにしない。画像1000枚の視覚確認、全読みの意味確認、30,000盤面の検証、10,000連戦、モバイル・IME・保存復旧・オフライン試験を本文に従って行い、証跡を残す。
人間による協力を必須の無期限待ちにしない。AIによる視覚レビューと人間の試遊を区別し、未実施の人間評価を実施済みと報告しない。

中断と完了
64枚、256枚は中間成果であり、完成ではない。生成機能がない場合の仮素材開発モードはprovisionalと表示し、コード・テストなど進められる部分を完成させる。権限/費用/ツールの真のブロッカーが残ったら、その依存部分だけを保留し、採用済みX/1000・未完了・必要な解除条件を明示する。
セッションが終わる前に成果物、各ジョブの状態、次の具体的な操作を保存する。次回はhashと実在ファイルを確認して再開し、承認済み画像を重複生成しない。無期限の連続実行やツールアクセスは前提にしない。
全必須受入条件を満たした場合にのみcompleteへ変更する。ビルド済みdist、ソース、1000画像、辞書、起動手順、検証結果、制作履歴を納品し、まず「今すぐ遊ぶ方法」を示してください。
